# Charm4py: Python-heavy versus thin-shim design — initial analysis (2026-11-06)

Written in the charm4py maintenance session on 2026-11-06 (Kale + Claude Fable 5.1),
in answer to: "Charm4py was designed by Juan with a philosophy of keeping most
implementation in Python. It could have been done, perhaps better, as a thin shim on
top of the complete Charm++ implementation. Is the difference significant?"

Short answer: the difference is significant, but not where one might first expect. It
is small on the per-message hot path and large in feature coverage, duplicated logic,
and the cost of adding anything new.

## What the current split actually is

Charm4py is about 6,200 lines of Python and Cython (charm.py 1289, charmlib_cython.pyx
1169, chare.py 926, pool.py 481, liveviz.py 407, threads.py 370, reduction.py 351,
wait.py 269, sections.py 201, entry_method.py 196, ccharm.pxd 130). On the Charm++
side it uses a hand-written "Ext" C API in src/ck-core/charm.h (about 60 functions
plus 12 callbacks registered from the binding: registerArrayMsgRecvExtCallback,
registerGroupMsgRecvExtCallback, registerChareMsgRecvExtCallback,
registerArrayBcastRecvExtCallback, registerArrayElemLeave/JoinExtCallback,
registerArrayResumeFromSyncExtCallback, registerArrayMapProcNumExtCallback,
registerCreateCallbackMsgExtCallback, registerPyReductionExtCallback,
registerMainchareCtorExtCallback, registerReadOnlyRecvExtCallback) and five generic
C++ classes: MainchareExt, GroupExt (charm++.h), ArrayElemExt (ckarray.h), ArrayMapExt
(cklocation.h), SectionManagerExt (charm++.h). Charm++ supplies the scheduler,
messaging, location management, array and group managers, built-in reductions, load
balancing, quiescence detection, CCS and user-event tracing. Python reimplements:

- Dispatch and marshalling: every message is a pickled tuple with a header, plus a
  direct-copy path ("dcopy") for buffer-protocol objects. The Python receive path
  (charm.py recvArrayMsg/recvGroupMsg/recvChareMsg) parses the header, looks up the
  object and calls the method.
- Sections and multicast: a Python SectionManager group (sections.py) builds its own
  spanning tree (charm.getTopoSubtrees, bfactor 4) and forwards messages through
  CkForwardMulticastMsg. CkMulticast is not used.
- Reductions: built-in types map onto Charm++ reducers through a Python conversion
  table (reduction.py populateConversionTables). Custom reducers run in Python on each
  tree level through one callback (registerPyReductionExtCallback).
- Group and array creation buffering (charm.py groupMsgBuf), coroutines (greenlet,
  threads.py), futures, channels, pool, the Ray API, and the SDAG-like `when` clauses
  (wait.py, AST rewriting).

## Where the difference is not significant

Ping-pong on one PE (tests/benchmark/pingpong.py, both elements on PE 0, scalar
argument, classic netlrts-darwin-arm8 build with error checking, charm4py main at
e97b12f, Python 3.13):

| path                      | round trip | per message |
|---------------------------|-----------:|------------:|
| plain entry method        |     4.5 us |      2.2 us |
| coroutine entry method    |    12.0 us |      6.0 us |

A Charm++ local message on this build costs roughly 1 us. Python adds only about 1 us
per plain message. Pickling of real payloads and the user's Python method body
dominate anything a thinner shim would save. A shim cannot change the pickle cost,
the GIL, or the fact that user code is Python. The coroutine path is the one real
inefficiency, since it creates a greenlet per invocation, and that is fixable within
the current design. (Cross-process +p2 on this Mac measured 129 us per round trip,
which is netlrts TCP loopback cost, not Python.)

Two things cannot be "thin" in any design:

1. Charm++ entry methods are compile-time artifacts generated by charmxi from .ci
   files, and Python classes exist only at runtime, so a generic C++ chare per kind
   with a runtime dispatch table is unavoidable. That is exactly what the Ext classes
   are.
2. Charm++ user-level threads (Cth) cannot run Python frames safely without
   greenlet-style save and restore of the interpreter's per-thread state, so greenlets
   stay.

## Where it is significant

- Feature coverage. Anything Charm++ has that Juan did not re-expose is absent:
  nodegroups, checkpoint and restart, CkMulticast, message priorities, entry method
  attributes (inline, expedited, immediate, nokeep), CkIO, per-entry Projections
  tracing, and now device messaging (CkDeviceBuffer, nocopydevice) and GPU load
  balancing attribution. Each one costs edits in four places: charm.h and ck.C, the
  Cython pxd and pyx, and the Python layer. That cost is why charm4py issue #309 (port
  GPU direct to charm4py over LCI) and the GPU LB attribution gaps exist.
- Duplicated semantics that drift. Sections, reductions, creation buffering and
  array-element lifecycle exist twice, once in C++ and once in Python. The reconverse
  port (charm4py #307) broke mostly in these duplicated paths.
- Language neutrality. The current Ext layer is shaped by Python's pickle format and
  Cython. A C++ "dynamic chare" layer with a stable, typed message format could serve
  Python, Julia, or Rust bindings equally.

## Shape of the alternative design

Three layers, with the middle one being the new work:

1. Charm++ core, unchanged.
2. A dynamic-chare layer in C++ ("CkDyn", working name), inside the Charm++ repo,
   language-neutral. Generic mainchare, group, nodegroup, N-dimensional array element,
   array map, and a section manager built on CkMulticastMgr. Registration takes
   per-class entry tables with attributes. The message format is a header plus typed
   slots: scalars by format code, buffer-protocol and device buffers by zero-copy
   (CkNcpyBuffer and CkDeviceBuffer), and an opaque tail for the binding's serializer.
   Callbacks, reductions with a foreign-reducer hook, pup through a function pointer
   (serving migration and checkpoint), priorities, QD, tracing with the registered
   method names, and LB hooks all live here.
3. A Python binding with nanobind instead of Cython, holding the dispatch table as
   method objects, converting arguments to slots, handling the GIL and exception
   propagation, and keeping greenlets for coroutines. Above it, the Python API layer
   borrowed from charm4py: decorators, proxies, Chare classes, `when`, channels, pool,
   Ray.

Deleted from today's charm4py: sections.py, most of the receive and creation code in
charm.py, the reduction conversion tables, and the Cython module. Kept: the
user-facing API and tests, which become the acceptance suite.

The main risk is ownership. Layer 2 must land in recharm and be maintained there, and
the charm4py CMake target already links against hybridapi and the LB modules, so this
is a Charm++ project as much as a charm4py one.
