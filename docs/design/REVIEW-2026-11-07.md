# Review of the charm4py thin-shim design (DESIGN.md, SPEC-4a.md, CkDyn step 1)

Reviewer: independent agent, 2026-11-07. Sources read: PROMPT.md, ANALYSIS-2026-11-06.md,
DESIGN.md, SPEC-4a.md, BENCHMARKS.md, surveys/*.md, charm/src/ck-core/ckdyn.h,
charm/doc/internals/ckdyn.md, the relevant parts of ckdyn.C, ckreduction.C, ck.C, ck.h,
cklocation.C, ckcheckpoint.C, trace-projections.C, reconverse cldb, the C++ test binding
(tests/charm++/ckdyn), charm4py `main` (charm.py, chare.py, entry_method.py, threads.py,
channel.py, charmlib_cython.pyx) and the tests named below. No code was run.

## Verdict

The architecture is right: a C hook table plus one typed message format, with Charm++
owning sections, reductions, pup and tracing, is a better split than the Ext API, and
the step 1 code is careful (contiguity check on entry indices, NULL-handle handling,
nested builders, the PUP::mem split). The weak point is the seam between CkDyn and
SPEC-4a. Several rules that each document states correctly break when combined, and
they break tests that are in the step 4a gate. I found six defects of that kind:

- creation acknowledgement sent twice, and sent before a coroutine constructor finishes;
- every reduction result sent to a callback without a reference number carries the
  reference number `(CMK_REFNUM_TYPE)-1`;
- the SPEC fast path accepts reduction and system views;
- `allreduce` loses its future id;
- a foreign reduction with one contribution is never marked as a result;
- singleton chares created through virtual ids have two identities.

Two of the three cost targets cannot be reached as specified:

- 1 MB: the builder copies every buffer twice and zero-fills it once.
- Coroutine: SPEC-4a moves the coroutine dispatch back into Python.

Beyond step 4a, three things should be settled before step 4b/4c code is written:

- checkpoint restart has no working resume path;
- `ResumeFromSync` became a synchronous re-entrant call;
- coroutine time after the first suspension is charged to `CkDynMgr`, both for the load
  balancer and for Projections.

The language-neutrality claim is weaker than DESIGN.md 8.7 says. The class-less hooks are
global. The C-binding row assumes a CthThread path that CkDyn does not have. Nothing
addresses runtimes that own signals.

## Findings

### F1. Creation is acknowledged twice, and too early for coroutine constructors

- Severity: blocking (step 4a gate: `thread_entry_methods/*`, `channels/*`, `collections/*`)
- Where: ckdyn.C:705-712 (ChareDyn), 811-815 (GroupDyn), 845-849 (NodeGroupDyn), 898-902
  (ArrayElemDyn); SPEC-4a 2.2 `construct`, 2.3 slow path, 3.2 `_construct`, 3.5 "Creation
  flags"; charm4py main entry_method.py:62-73.
- What is wrong:
  - CkDyn acknowledges a `CKDYN_MSG_CREATION` constructor itself. GroupDyn, NodeGroupDyn
    and ArrayElemDyn contribute a nop reduction to the FUTURE callback; ChareDyn calls
    `CkDynFutureSet`.
  - SPEC-4a also sets `BLOCK` on the same messages (`BLOCK|BCAST|CREATION` for
    groups/arrays, `BLOCK|CREATION` for singletons). It builds `header[b'block']`,
    `header[b'bcast']` and `header[b'creation']` for `_construct`, which calls `em.run`.
    Today's `_run` then acknowledges as well: for `b'bcast'` it calls
    `charm.contribute(None, None, blockFuture, obj)` (entry_method.py:66-72); otherwise
    it calls `blockFuture.send(ret)`.
  - Result for a singleton: a second deposit to a one-value future, which
    `depositFuture` turns into `Charm4PyError('No pending future with fid=...')`
    (threads.py:341-346).
  - Result for a collection: two independent reductions completing on the same future.
  - Separately, CkDyn acknowledges when `construct` returns. For a `@coro __init__` that
    returns at its first suspension. Today the contribution happens in `_run` after
    `__init__` completes.
- Why it matters:
  - `tests/thread_entry_methods/threaded_ctors2.py` asserts inside a blocking array
    constructor and relies on `awaitCreation` waiting for it. With the early
    acknowledgement, main reaches `exit()` first.
  - If some elements block in `__init__` and others do not, the acknowledgement and any
    reduction the constructor makes are contributed in a different order on different
    elements. Charm++ matches contributions by sequence number, so nop and user data mix.
- Suggestion:
  - Have one owner of the acknowledgement. The binding can own it: drop
    `CKDYN_MSG_CREATION` handling from the constructors, or keep it only for bindings that
    ask for it with a class flag.
  - Alternatively keep it in CkDyn but expose `CkDynAckCreation(target)`. The binding
    calls it when the constructor really finishes, which includes the end of a coroutine.
  - Either way SPEC-4a must not set BLOCK and CREATION together.

### F2. Reduction results to callbacks without a reference number get a bogus FUTURE slot

- Severity: blocking (step 4a gate: `reductions/*`, `callbacks/*`)
- Where:
  - ckreduction.C:700 and 1130: `CkSetRefNum(result, result->getUserFlag())`, where
    `userFlag` defaults to `(CMK_REFNUM_TYPE)-1` (ckreduction.h:443-452; ckarray.h:385-392).
  - ckcallback.C:374-416: the refnum is overwritten only when `hasRefnum`.
  - ckdyn.C:513-514 and 527-529: any nonzero ref becomes a synthesized FUTURE slot.
  - ckdyn.C:1160: TARGET callbacks set a refnum only when `cb->refnum != 0`.
  - DESIGN.md 3.7, "The rule is safe only because CkDyn controls every path that sets
    `ref`".
- What is wrong: a plain `self.contribute(x, Reducer.sum, self.thisProxy[0].done)`
  arrives at `done` as a REDRESULT view with ref 0xFFFFFFFF (0xFFFF on the 16-bit CI
  build). The view therefore has a synthesized `FUTURE (CkMyPe(), 0xFFFFFFFF)` slot. The
  design's safety argument missed the reduction manager's own `CkSetRefNum`. The C++ test
  binding does not catch this because every TARGET callback in ckdyntest.C carries a
  refnum (ckdyntest.C:457-458).
- Why it matters: under SPEC-4a's fast path (F3) the FUTURE slot becomes an extra
  positional argument, so `done(self, result)` raises `TypeError`. Any binding that trusts
  "nonzero ref means future" deposits into id 0xFFFFFFFF.
- Suggestion:
  - In `CkDynMakeCallback`, always set `hasRefnum` on the callbacks CkDyn builds, with
    refnum 0 when there is no future, so `CkCallback::send` overwrites the user flag.
  - Also treat `(CMK_REFNUM_TYPE)-1` as "none" in `viewReduction`/`viewSys`.
  - Add a C++ test with a TARGET callback without a refnum.

### F3. The SPEC-4a fast path accepts REDRESULT and SYS views

- Severity: blocking (step 4a)
- Where: SPEC-4a 2.3, fast-path condition `hflags == 0` with
  `hflags = view->hdr ? view->hdr->flags : 0`; SPEC-4a section 1 conversion table;
  ckdyn.C:501-536.
- What is wrong:
  - REDRESULT and SYS views have `hdr == NULL`, so they take the fast path, which
    converts slots with the section 1 table.
  - A REDRESULT BUFFER slot has `ndim 0` and `len = n * elemsize`. The table turns it
    into a 0-d numpy array, which is one element, and silently drops the rest.
  - The special rule of SPEC section 1 for reduction results (None for empty, a scalar
    for one element, else an array) is only in the slow path.
  - The synthesized FUTURE slot becomes a positional argument (F2, F4).
- Why it matters: every reduction delivered to an entry method gives a wrong value or a
  wrong argument count.
- Suggestion: add `view->kind == CKDYN_MSGKIND_DYN` to the fast-path condition, or give
  REDRESULT its own small C++ path that applies the section 1 rule.

### F4. Collective futures (`allreduce`) lose their id

- Severity: blocking (step 4a gate: `reductions/allreduce.py`)
- Where: SPEC-4a 3.4 ("CollectiveFuture.send keeps using `_coll_future_deposit_result`"),
  2.3; charmlib_cython.pyx:1076-1077, 1113-1115 (today the fid is inserted as the first
  argument); charm.py `_coll_future_deposit_result(self, fid, result)`.
- What is wrong: today the callback-message builder prepends `fid` to the arguments. In
  CkDyn the fid is only in `view.refnum`, plus a synthesized FUTURE slot that comes after
  the BUFFER slot. Neither SPEC path passes `view.refnum` to a TARGET entry:
  - The fast path passes `(value, Future)`, in the wrong order and with the wrong type.
  - The slow path passes `[value]`.
  - A nop `allreduce()` (SYS view) passes a Future object as `fid`.
- Suggestion: specify one rule. For a REDRESULT, SYS or foreign-result view delivered to
  an entry method with a nonzero refnum (after F2's fix), the binding prepends
  `view.refnum` as an int, which matches today. Alternatively route collective futures
  through FUTURE callbacks keyed by `(fid, obj)`. Add a test that checks the value, not
  only completion.

### F5. A foreign reduction with a single contribution is never marked as a result

- Severity: blocking (step 4a, `reductions/*` at 1 process; any gather or custom reducer
  over one element or one PE)
- Where:
  - ckreduction.C:866-872: `if (nMsgs == 1 && reducer != set && reducer != tuple) ret = msgArr[0];`.
    The reducer function is not called, and a nop contribution does not count toward
    `nMsgs` (ckreduction.C:829).
  - SPEC-4a 1 and 1.1: `PYMSG_REDRESULT` is set only by the reduce hook.
  - SPEC-4a 2.2 `future`, 2.3 slow path.
- What is wrong: when the reduce hook never runs, the final message is the raw
  contribution, without `PYMSG_REDRESULT`. `future` then passes `rid = -1` and skips
  `postprocess`. `gather` returns the preprocessed `(index, value)` form instead of the
  values. The same happens when one element contributes through `_bcast_exc_reducer` and
  every other element contributes nop, which is exactly the exception-in-broadcast case.
  Today's contributions carry `custom_reducer` in their own header (pyx 1132-1163), so
  today's pass-through result is still recognized.
- Suggestion: mark contributions, not only results. Set a binding flag "foreign payload"
  on every foreign contribution, with the reducer id in `user_id`. Make the receive side
  apply `postprocess` whenever the flag is present. Require the reduce hook's output to
  have the same form as its inputs, so a result can pass through a level unchanged. Add
  a C++ test with one contributor.

### F6. `Chare(C)` singletons have two identities (virtual id at the creator, real id inside)

- Severity: blocking for 4a as specified (`channels/test1.py` is in the gate); a design
  decision (5.4 item 13) for Kale.
- Where: ckdyn.h:420-422 ("*out receives a virtual chare id ... construct receives the
  real id"); ck.C:805-840, 1212-1222, 1760-1777; ck.h:196-232 (VidBlock); SPEC-4a 2.5,
  3.2 `_construct` (stores `charm.chares[cid]` under the real id); tests/channels/test1.py:11, 23.
- What is wrong:
  - The proxy the creator gets names `(-(creatorPe+1), vidIndex)`. The chare's own
    `thisProxy` names `(realPe, ptr)`, and the two proxies compare unequal.
  - `channels/test1.py` asserts `data[1] == other`, where one side is a real-id proxy and
    the other a vid proxy.
  - `Channel` matches pending channels by proxy (channel.py:6-24), so a channel between
    a creator and its singleton never establishes and the test hangs.
  - The same test uses `self.thisProxy[self.thisIndex]` inside a singleton. `thisIndex`
    and proxy indexing exist today only because singletons are one-element arrays;
    SPEC-4a defines `thisIndex` only for groups and arrays.
  - Every send through a vid from a PE other than the creator is a ForVidMsg to the
    creator, which forwards it with `CldEnqueue`. That is two hops for the life of the
    chare.
  - With `onPE` omitted, reconverse's `cldb.rand.cpp:89-96` places the chare on a random
    PE. Today it goes to the home PE of index 0, usually PE 0.
- Why it matters:
  - The latency of every remote singleton call doubles on multi-process runs.
  - Proxy equality and hashing, which channels, `when` conditions and user dicts use,
    stops working.
  - Code that treats a singleton like a one-element array (thisIndex, `proxy[i]`)
    breaks, and 5.4 item 13 does not list that change.
- Suggestion:
  - Give the constructed chare the vid as its identity. CkDyn can pass it in the
    construct target; `NewVChareMsg` carries `getVidPtr()` and `getByPe()`. Then every
    proxy agrees.
  - Optionally add a CkDyn-side cache that replaces a filled vid with the real id on the
    sending PE, after a `FillVidMsg`-style notification.
  - Keep `thisIndex == (0,)` and `proxy[0] is proxy` on singleton proxies for
    compatibility, or list the removal in 5.4.
  - Run `channels/*` against `Chare(onPE=)` before declaring item 13 done.

### F7. The 1 MB target cannot be met: the builder copies each buffer twice, plus a zero-fill

- Severity: blocking for the 4a performance gate (SPEC-4a 5, DESIGN.md 7.4)
- Where: ckdyn.C:382-393 (`CkDynMsgAddBuffer`: `b->data.resize(off + 8*ndim + len)`, which
  value-initializes, then `memcpy` into the vector), 430-447 (`writePayload`: a second
  `memcpy` into the message), 418-423 (`CkDynMsgReserveTail` likewise); DESIGN.md 3.4
  ("copies once into the final message"; "a message whose payload is only scalars takes
  a path that allocates the message first", which is not implemented).
- What is wrong: a 1 MB numpy send writes 1 MB three times: zero-fill, copy in, copy out.
  On BENCHMARKS.md's numbers (20.4 us per 1 MB copy) that is about 45-60 us on the send
  side. pingpong.py re-sends the received array, so every message pays it. Today's
  number is 59.6 us. The target of about 23 us needs exactly one copy.
- Suggestion:
  - Record BUFFER and BYTES slots in the builder as `(ptr, len)` references, valid until
    `Finish`. Compute the total, allocate the message once, and copy each source once.
  - Pickled tails: let `CkDynMsgReserveTail` be followed by `Finish`-time placement, or
    give the binding a two-phase API (`size`, then `write into message`). Today a pickle
    is copied into the tail vector and then into the message, on top of `pickle.dumps`'s
    own allocation.
  - This is a change to step 1 code. Do it before 4a measures, or the gate fails for a
    reason unrelated to the binding.

### F8. The coroutine target (1.4 us) is not reachable with SPEC-4a's Python-driven coroutine path

- Severity: should fix before 4a is called done (re-baseline the target or move the path back to C++)
- Where: DESIGN.md 4.5 and 7.4 (target = plain 1.0 + one pooled switch pair 0.37); SPEC-4a
  2.3 (THREADED goes to the slow path, which builds a header dict and an args list and
  calls `charm._invoke`), 3.3 `_run_th`, 2.6.
- What is wrong: the 1.4 us figure assumes the C++ `deliver_slow` drives the worker
  directly (DESIGN 4.4/4.5). SPEC-4a instead runs this chain:
  1. a C++ dict and list build;
  2. Python `_invoke`, then `invokeEntryMethod`, then `em.run`, which is `_run_th`;
  3. `getattr(obj, 'migratable')`;
  4. `_ckdyn.set_migratable` twice (F9);
  5. `_ckdyn.spawn`, then Python `_run` with `getcurrent()` and two greenlet attribute
     stores;
  6. `getattr(obj, name)(*args)`;
  7. the header check, then back through four Python frames.

  That is roughly five Python calls plus two runtime calls on top of the 0.37 us switch.
  Today's measurement puts the non-greenlet coroutine bookkeeping at about 1.6 us
  (6.14 - 2.27 - 2.3 saved). SPEC keeps most of it. Expect 2-2.5 us, not 1.4.
- Suggestion: either implement DESIGN 4.5 as written, with C++ choosing the worker and
  calling the method (and `_numthreads` in the ChareBase C slot), or state the target as
  about 2.2 us for 4a and 1.4 us for a later step. Keep the functional gate separate from
  the performance gate so 4a can close.

### F9. `set_migratable` is toggled on every coroutine invocation, not on suspension

- Severity: should fix before 4c
- Where: SPEC-4a 3.3 (`_run_th` calls `set_migratable(False)` when `_numthreads` goes
  0→1 at spawn); DESIGN.md 4.5 item 1 ("count of coroutines that are suspended ... none
  for coroutines that never block"); cklocation.C:2307-2313 (LB database update);
  cklocation.C:1926-1945 (`AtSync`).
- What is wrong:
  - Every `@coro` call makes two runtime calls that update the LB database, which costs
    time on the hot path.
  - The bigger problem is behavior. `examples/particle/particle.py:131-137` and similar
    code call `self.AtSync()` from inside a coroutine and then return. Under SPEC-4a the
    element is non-migratable at the moment it calls `AtSync`. If the local barrier
    completes inside that call and the strategy reads the LB database's migratable flag
    then, the element is excluded from balancing.
- Suggestion: toggle in `pauseThread`/`_resumeThread`, that is on real suspension, as
  DESIGN 4.5 says. Verify with a test that a coroutine calling `AtSync` and returning is
  still migrated by `RotateLB`.

### F10. `ResumeFromSync` is now a synchronous, re-entrant call into Python

- Severity: should fix before 4c (`migration/*`)
- Where:
  - ckdyn.C:914-918 (`ArrayElemDyn::ResumeFromSync` calls the hook).
  - SPEC-4a 3.2 `_resume_from_sync`, which calls `invokeEntryMethod` directly.
  - cklocation.C:1933-1938: `AtSync` with no barrier receivers calls `ResumeFromSync()`
    inline, inside the caller's `AtSync`.
  - cklocation.C:2035-2053: the barrier's resume loop.
  - Today: charmlib_cython.pyx:1036-1043 self-sends a message to the `resumeFromSync`
    entry.
- What is wrong:
  - `tests/migration/test_migrate.py` has `resumeFromSync` call `self.start()`, which
    calls `AtSync` again. Without a balancer (or when the meta-LB decides not to
    balance), each iteration nests one level deeper inside the previous `AtSync`, which
    leads to unbounded recursion.
  - With a balancer, user Python runs inside the LB barrier's client loop. It can send,
    insert, destroy or call `AtSync` there. C++ users can do the same, but charm4py
    users never had to know, because the call was asynchronous.
- Suggestion: keep today's semantics. `ArrayElemDyn::ResumeFromSync` (or the binding)
  sends a message to the element's resume entry instead of calling it. The hook can stay
  for bindings that want the synchronous form.

### F11. Checkpoint/restart has no working resume path for charm4py programs

- Severity: should fix before 4c (the `checkpoint/restart.py` gate)
- Where: DESIGN.md 3.7 (last paragraph: the binding's checkpoint callback is a FUTURE
  callback, because `sendChare` callbacks hold a pointer); 4.5 items 4-5 (after restart,
  "execution resumes through the checkpoint callback"; futures from before the restart
  raise); 3.10; ckcheckpoint.C:443-466, 480-541.
- What is wrong:
  - The restart path invokes the stored checkpoint callback.
  - If that is a FUTURE callback, it targets a future id from the checkpointed run.
    DESIGN 4.6 makes `deposit` raise for such ids, and no coroutine is waiting on it
    anyway.
  - Every charm4py program's control flow lives in `main`, which is a suspended
    coroutine and is not restored. So after `+restart` nothing runs.
  - The design's own rules exclude the two obvious targets: a future (stale) and a main
    chare entry (pointer).
- Suggestion:
  - Make `charm.checkpoint(dir, resume)` take an entry method of a group, array or main
    chare as `resume`, and route a main-chare target through `CkDynMgr` by chare index,
    not pointer.
  - On the original run, also deposit to an optional future so `main` can continue.
  - Write `tests/checkpoint/restart.py` to exercise `resume` after `+restart`.
  - Note that `CkPupChareData` restores plain chares per PE. A restart with a different
    PE count, which shrink/expand is, drops ChareDyn singletons that lived on removed
    PEs and their VidBlocks. That conflicts with decision 10 unless singletons stay
    arrays when shrink/expand is enabled.

### F12. Coroutine time after the first suspension is attributed to `CkDynMgr`, for both LB and Projections

- Severity: should fix before 4b (it undermines decision 10 and the GPU-attribution goal)
- Where: DESIGN.md 3.12 (push/pop only around kernel launches), 3.13 (coroutines);
  ckdyn.C:1344-1347 (`CkDynTraceBeginEntry` uses `_TRACE_BEGIN_EXECUTE_DETAILED` with no
  object and is called while the deposit entry is already being traced); SPEC-4a 3.4
  `_resumeThread` (no push).
- What is wrong:
  - A resumed coroutine runs inside `CkDynMgr::deposit`, or inside whatever entry
    resolved the future. `CkDeliverMessageFree` has pushed `CkDynMgr`, a non-migratable
    group, as the running object.
  - In charm4py's style (coroutines that block on futures and channels every iteration)
    most element work after the first suspension is background load that the balancer
    cannot move and Projections shows as `CkDynMgr.deposit`.
  - `CkDynTraceBeginEntry` would nest a BEGIN_PROCESSING inside another, which
    trace-projections does not represent.
- Suggestion:
  - Bracket every greenlet resume with `CkDynCallstackPush/Pop(gr.obj)` in the binding.
  - Use Charm++'s thread tracing (the suspend/resume events used for `[threaded]` entries
    under `CthTraceResume`) rather than begin/end execute. Alternatively end the outer
    entry's bracket before beginning the coroutine's.
  - State it as a step 4a requirement, since it changes load numbers that tests in
    `appspector/` read.

### F13. Projections parity is overstated: ndims-0 arrays lose element indices, broadcasts are not traced per element

- Severity: should fix before 4b
- Where:
  - SPEC-4a 3.2 (arrays registered with `ndims = 0`).
  - ckdyn.C:195-200.
  - trace-projections.C:706-716: the index is recorded only for `ndims >= 1`.
  - trace-common.C:303.
  - ckdyn.md "Array broadcasts": the `deliver_many` path skips `CkDeliverMessageFree`, so
    there is no per-element trace event.
  - DESIGN.md 0 item 10, 3.13 ("element indices exactly as ... charmxi").
- What is wrong: with ndims 0, no array element index is recorded for any charm4py array
  and the `.sts` CHARE line says 0 dimensions. Array broadcasts, a large share of
  charm4py traffic, show up as one array-manager event per PE.
- Suggestion:
  - In trace-projections, take the dimension count from the element's `CkArrayIndex`
    when the chare's `ndims` is 0. This is a few lines and general.
  - Have `deliver_many` callers (or CkDyn around each element) emit begin/end execute
    per element when tracing is on.
  - Make the step 4a Projections gate check an array index in the log, not only the
    `.sts` names.

### F14. The GIL is held while calling into the runtime; lock-order inversion once a process has several PEs

- Severity: should fix before nodegroups and multi-PE processes (step 2 / step 7); a
  wrong statement in DESIGN.md 4.4 now.
- Where: DESIGN.md 4.4 ("Nothing in CkDyn or Charm++ runs with the GIL held except
  inside a hook, so CkDynSend* calls made from inside a Python method ... never
  deadlock"); 3.6 (nodegroup entries "fine because every hook takes the GIL");
  ckreduction.C:2198-2205 and 2155-2158 (`CkNodeReductionMgr` holds `lockEverything`
  while `finishReduction` runs the reducer, which is the foreign reduce hook).
- What is wrong:
  - Every `_ckdyn.*` call from Python runs Charm++ code with the GIL held.
  - Deadlock scenario: thread A (PE 0, in Python) contributes to a nodegroup reduction
    and blocks on `lockEverything`. Thread B (PE 1) holds `lockEverything` and is inside
    `hooks.reduce` waiting for the GIL.
  - The same pattern applies to any runtime lock under which a hook can run: the node
    queue, the location manager in SMP mode, CkMulticast.
  - `CkExit` also enters `CsdScheduler(-1)` with the GIL held, so other PE threads of
    the process cannot run hooks while exit proceeds.
- Suggestion:
  - Either release the GIL around every `_ckdyn` call that can take a runtime lock (this
    costs about 0.1 us per send), or keep "one PE per process" as a hard rule and make
    `_ckdyn.start` refuse `CmiMyNodeSize() > 1` until step 7 audits the locks.
  - Separately, measure the per-hook `PyGILState_Ensure/Release` against an alternative
    for the one-PE case: hold the GIL while the scheduler is busy and release it in
    `CcdPROCESSOR_BEGIN_IDLE` / `END_IDLE` callbacks. That removes two mutex operations
    per message and still lets Python threads run when the PE is idle.

### F15. The ABI is not yet multi-binding or multi-language in the ways DESIGN.md 8.7 claims

- Severity: should fix before step 2 freezes `CKDYN_API_VERSION 1`
- Where: ckdyn.h:313-350, ckdyn.md "The hook table" ("the hooks without a class ... are
  always taken from g_hooks"); DESIGN.md 8.7 requirement (b), table row "C";
  SPEC-4a section 1 (typecode in `CkDynSlot.reserved`).
- What is wrong:
  1. Per-class `hooks` exist, but `future`, `reduce`, readonlies, `register_classes`,
     `error` and CCS are process-global. Two bindings in one process would receive each
     other's future deposits and foreign reductions. Future ids and reducer ids have no
     binding namespace.
  2. The C row says blocking entries use `CthThread` "through `CKDYN_EP_THREADED`, which
     CkDyn passes through". CkDyn only passes the flag through. It never creates a
     CthThread, so a C, C++ or Rust binding has no way to block in an entry method.
  3. NULL is overloaded as "not constructed" (constrained groups, ckdyn.C:633-638). A
     binding whose handles are small integers starting at 0 breaks silently.
  4. `CkDynHooks` has `version` but no size field, so adding any hook is an incompatible
     change.
  5. SPEC-4a stores the `array.array` typecode in `CkDynSlot.reserved`, a field the ABI
     reserves for CkDyn. Use `tag` bits.
  6. Charm++ installs SIGSEGV/SIGBUS/SIGINT handlers. Julia uses SIGSEGV for GC
     safepoints, and the JVM and .NET use signals too. Nothing lets a binding stop
     Charm++ from installing them.
  7. Structs copied "as bytes" into messages (`CkDynTarget`, `CkDynCallback`) contain
     C `enum` fields and a union with `void*`. Their layout is ABI, but they are not
     fixed-width types.
  8. Views of REDRESULT/SYS messages point at synthesized slots on CkDyn's stack, so a
     retained view's slot array is invalid after the hook. The header says nothing about
     this.
- Suggestion:
  - Add a binding handle: `CkDynRegisterBinding(hooks) -> id`, with the id carried in the
    upper bits of `user_id`/future ids.
  - Add `size_t size` to `CkDynHooks`, use fixed-width integer types for the kind fields,
    and document "handle must be non-NULL" or add an explicit constructed bit.
  - Add an option `CKDYN_EP_CTHREAD` that runs the entry in a CthThread, as charmxi does.
  - Add a start-up option to skip signal handlers.
  - Fix the C row of 8.7.

### F16. numpy arrays with non-native byte order are silently reinterpreted

- Severity: should fix before 4a closes (silent data corruption)
- Where: SPEC-4a section 1 (dtype to `elem` mapping by kind and size); today
  `rebuildNumpyArray` reconstructs from the dtype string, which keeps the byte order.
- What is wrong: `>f8` maps to F64, and the receiver builds a native-order view, so the
  values are garbage. The same applies to unaligned or non-standard dtypes that match by
  size.
- Suggestion: map only `dtype.isnative` arrays with standard alignment to slots; send
  everything else through the pickle tail.

### F17. Sections plan: open semantics the step 2 code will have to decide

- Severity: should fix before step 2 code
- Where: DESIGN.md 3.9, 3.7 (collective futures on sections), 5.2, 5.4 item 10.
- What is wrong:
  1. `allreduce` on a composite (combined) section needs a shared id. `CkDynSectionRedNo`
     is per section, and a composite has no cookie.
  2. An element that belongs to two parts of a composite would contribute twice. The
     design does not say whether `combine` is a union or a disjoint concatenation.
  3. Migration of section members (item 10) relies on CkMulticast's rebuild and on
     pupped `CkSectionInfo` cookies whose `val` points into another PE's memory. The
     step 2 test list includes RotateLB migration and section reductions, but not
     together.
  4. DESIGN.md 5.2 calls `CkDynSectionCreateCross`, which does not exist; the API is
     `CkDynSectionCombine`.
  5. Every send from a non-root PE goes through `CkDynMgr[root]`. That is the same as
     today, but it makes the root PE a hotspot for sections used as communicators.
- Suggestion: decide (1) and (2) in the design. Add a C++ test with section reductions
  across `RotateLB` migrations under `+randomized_msgq`. Keep `sections.py` on a branch
  until 4b passes at 4 processes, in case CkMulticast on reconverse needs more fixes like
  #4131.

### F18. Migration plan: step 4a is far larger than the other sub-steps, and gates mix function with speed

- Severity: should fix in the plan
- Where: DESIGN.md 7.1 step 4 table, 7.4; SPEC-4a 5.
- What is wrong:
  - 4a covers the whole binding, the Python cut-over, reductions, futures, callbacks,
    coroutines, exceptions, readonlies and topology, and its gate includes performance
    targets. 4b-4d are small by comparison.
  - Given F1-F8, the 4a gate will fail first on things outside the binding: step 1
    semantics and the builder.
  - Step 8's gate "shrinks from 4 to 2 PEs and expands back in one process" is not a
    shrink/expand scenario as Charm++ defines it, which is a relaunch with a new process
    count. Reconverse also needs launcher support for relaunch, which nothing in the
    plan assigns.
  - Step 3's GPU gate is "run by hand and recorded", so nothing prevents regression
    after step 3.
- Suggestion:
  - Split 4a into 4a-1 (plain entries, futures, reductions, callbacks, exceptions; a
    functional gate only) and 4a-2 (coroutine pool, performance targets).
  - Fix F1-F5 and F7 in a small charm PR first.
  - Restate step 8's gate as a relaunch with a different process count under lcrun or
    the new launcher, and list the launcher work.
  - Schedule a periodic GPU job, for example on Delta, for step 3's test.

### F19. Fast-path dispatch semantics differ from today's `getattr(obj, name)(*args)`

- Severity: minor
- Where: SPEC-4a 2.3 (vectorcall on the class's function), 3.2 `registerInCharmAs`
  (`func = getattr(C, em.name)`); entry_method.py:47.
- What is wrong:
  - An instance attribute that overrides a method, a method replaced on the class after
    registration, or a `staticmethod`/`classmethod` entry now behaves differently.
  - The fast path flushes wait queues whenever `_cond_next` is set and ignores
    `charm.options.auto_flush_wait_queues` (charm.py `invokeEntryMethod`).
  - It does a `PyObject_GetAttr(obj, "_cond_next")` per message, which walks the class
    MRO before the instance dict, about 30-50 ns.
- Suggestion: honor the option. Keep a C-level "has pending when-queue" bit on
  `ChareBase` instead of the attribute lookup. Document that entry methods are bound at
  registration.

### F20. Smaller items

- Severity: minor
- Items:
  - Argument aliasing changes. Today all arguments are one pickle, so `m(a, a)` or an
    array that appears both at top level and inside a list arrives as one object. With
    per-slot conversion it arrives as two. Note it in 5.4.
  - SPEC-4a should require `CkDynMsgAbandon` on every error path during argument
    conversion. Otherwise the cached builder stays `inUse` and every later send
    allocates a new builder (ckdyn.C:323-327).
  - A pooled greenlet keeps `gr.obj` (and `gr.notify`) from its last task. That holds a
    destroyed or migrated-away chare alive until the greenlet is reused. Clear them when
    the task ends.
  - A retained view keeps the whole message alive. A small array kept from a message
    that also carried large arrays pins all of it. Document it, or copy views below a
    size threshold.
  - Document drift:
    - DESIGN.md 3.17 lists `CkDynCcsSendDelayedReply` twice.
    - DESIGN.md 3.6 says `MainchareDyn` creates `CkMulticastMgr`; the code does not.
    - ckdyn.md "Registration" says `ndims` is 1 to 6, while later text and ckdyn.h allow 0.
    - ckdyn.md "Limits" still says future ids are 16 bits.

## Claims checked and found correct

- Message index and ep widths: `msgIdx` 8 bits, `epIdx` 16 bits; CkDyn uses two message
  types (DESIGN 3.5, 8.4).
- 4D-6D array indices are stored as shorts, and `mkIndex` checks the range (ckdyn.C:70-78).
- `CkLocRec::setMigratable` updates the LB database (cklocation.C:2307-2313), as DESIGN
  4.5 item 1 assumes.
- `CkPupChareData` checkpoints plain chares and VidBlocks and requires a migration
  constructor (ckcheckpoint.C:480-541). ChareDyn has one.
- A nodegroup `EXCLUSIVE` entry uses the same try-lock-and-resend protocol as charmxi
  (ckdyn.C:858-872).
- The nokeep ownership rule, and `CmiFree` rather than `CkFreeMsg` for release, match
  msgalloc and the practitioner notes.
- The constrained-group NULL handle drops broadcasts and callback results and reports
  point-to-point sends (ckdyn.C:633-638).
- `CkDynArrayInsert` takes the class from the constructor ep. Group and array
  constructors take the class from the header ep, not `_currentChareType` (ckdyn.C:776-790).
- The ndims-0 change affects only tracing among runtime users of `ChareInfo::ndims`
  (grep of ck-core, ck-ldb, ck-perf).
- The 32-bit refnum needs no `CkCallback` code change. All uses are `CMK_REFNUM_TYPE`.
- Disposition table 3.15 against survey-ext-api.md Tables A-C: every listed Ext symbol
  and every `CMK_CHARM4PY` branch has a disposition.
- Only charm4py uses the Ext API (survey section 4); the method is sound.
- The tests that 5.4 items 6 and 12 name do set the options and read the internals listed.
- Today `allreduce` uses `redNo % 65535 + 1`, and future ids are 32-bit (chare.py:124-147,
  threads.py:10, 317-325), as DESIGN 3.7 says.
- The reconverse `CLD_ANYWHERE` path randomizes placement (cldb.rand.cpp), so
  `onPE=-1` does reach a "seed balancer". It is random placement, not load-based.

## Questions I could not settle without running code

1. Does reconverse deliver messages received from LCI in transport-owned buffers? The
   practitioner notes ("Zero-copy has a hidden cost cross-node") say interior references
   pin receive buffers. If so, a program that keeps received numpy views for a long
   time could exhaust LCI's receive pool at 2+ processes. Test: keep 10,000 received
   1 KB arrays alive across `lcrun -n 2`.
2. Does the LB stats collection read the migratable bit synchronously inside the last
   local `AtSync` (TreeLB and CentralLB)? This decides whether F9 is a correctness bug or
   only a performance one.
3. What is the real cost of `PyGILState_Ensure/Release` per hook on Python 3.13 macOS,
   against holding the GIL and releasing it only when idle (F14)? Measure with an empty
   entry method.
4. Does greenlet 3.x support free-threaded CPython well enough for step 7, and does
   `PyGreenlet_SetParent` across PE threads work at all?
5. After F2's fix, is any other runtime path setting `ref` on messages to CkDyn
   entries? Candidates: CkMulticast `userData = -1` defaults, `CkFuture`, CkCallback
   from HAPI. A C++ test that asserts `refnum == 0` for every non-future delivery would
   settle it.
6. Does the plain 1.0 us target hold once F3's kind check, F19's attribute lookup and
   F15's per-call checks are added? The estimate in 7.4 has no measured binding
   component yet.
7. Does `CkStartCheckpoint` on reconverse (one process, `+pe 4`) restore groups created
   in the main chare constructor before `CkDynMgr`? Startup order matters for
   `_ckdynMgrGID` as a readonly.
